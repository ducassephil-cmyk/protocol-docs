## 1. Chile's Regulatory Framework — What Applies to GreyValley

### Ley 21.521 (Fintech Law, January 2023)
The most relevant law. Regulates:
- **Crowdfunding platforms** — does not apply directly to GreyValley
- **Alternative transaction systems (SAT)** — possibly applies to the ODL and swap
- **Custody of financial instruments and virtual assets** — **the main risk**
- **Order-routing services** — possibly applies to the Corridor

### CMF (Comisión para el Mercado Financiero — Chile's financial markets regulator)
Regulates the activity. Has the authority to:
- Authorize, suspend, or cancel the operation of regulated entities
- Require minimum capital, conduct manuals, audits
- Fine up to 15,000 UF (Unidad de Fomento, an inflation-indexed Chilean monetary unit) per serious infraction

Ley 21.521 creates a **regulatory sandbox** (Art. 90+) allowing operation for up to 24 months under CMF supervision while the business model is evaluated. **This is the recommended entry path for GreyValley.**

### UAF (Unidad de Análisis Financiero — Chile's Financial Analysis Unit)
Regulates AML/CFT. Applies to entities handling virtual assets as PSAVs (Proveedores de Servicios de Activos Virtuales — Virtual Asset Service Providers). Koywe absorbs much of this risk by handling on-ramp KYC/KYB.

### Banco Central de Chile (Central Bank of Chile)
Regulates payment systems. sCLP (synthetic Chilean peso) might need a Central Bank ruling if it scales. The ckUSDC and ckBTC canisters are, in principle, foreign tokens, not Chilean monetary issuance.

## 3. Technical Mitigants — Architecture That Weakens the Custody Argument

### Mitigant 1: tECDSA — no human private key

The EVM wallet's private key **does not exist** on any GreyValley server. It is distributed as shares among 28+ independent nodes of the ICP subnet (operated by different entities in different jurisdictions). To sign a transaction, the ICP protocol requires the threshold — no individual node (nor GreyValley) can do it alone.

**Legal argument:** GreyValley does not "hold" the EVM wallet's key in any traditional sense — this is analogous to how a DeFi protocol like Maker "holds" the ETH collateral without any company custodying it.

**Limitation:** the argument is novel in Chile and has no case law. A conservative regulator may disregard it.

### Mitigant 2: EVM smart contract instead of an EOA

Instead of an EOA-type EVM wallet (Externally Owned Account, controlled by tECDSA), deploy an **EVM contract** (custom escrow or Gnosis Safe) with immutable rules:

```solidity
// EVM contract rule
function releaseUSDC(address recipient, uint256 amount, bytes calldata icpProof) external {
    // Only callable from the bridge_canister canister's tECDSA address
    require(msg.sender == KOYWE_BRIDGE_TECDSA_ADDRESS, "Unauthorized");
    // Only releases if there is proof of a ckUSDC burn on ICP
    require(verifyIcpBurn(icpProof), "Invalid ICP proof");
    usdc.transfer(recipient, amount);
}
```

**Does the Gnosis Safe "have custody" of the USDC?**
Yes, the USDC lives at the Safe's address. But the relevant legal question isn't who holds the asset but **who can move it**:
- Safe with human signers (GreyValley team as signers): human custody → **BAD**
- Safe where the **only authorized signer is the `bridge_canister`'s tECDSA address**: no human can release the USDC without going through the algorithm → **GOOD**

The correct architecture: the Safe (or custom escrow) accepts transactions **only** from the address derived by the canister's tECDSA. No human signers. This turns custody from "a company controls the funds" into "an algorithmic protocol controls the funds."

### Mitigant 3: Transit wallet — not a holding wallet

The USDC **should not remain** in the EVM wallet for longer than the seconds it takes for the Koywe webhook → tECDSA verification → ckUSDC mint. It's an almost instantaneous transit, not sustained holding.

**Legal argument:** an asset that passes through automatic transit over seconds with no human intervention can hardly be characterized as "fund management."

### Mitigant 4: Governance with timelock (the most powerful for the regulator)

See §5 below. If no canister upgrade can be executed without governance approval + a 48h wait, the GreyValley team does not have unilateral control over the funds. This argument is the most understandable for a non-technical regulator.

## 4. Recommended EVM Architecture — Decision Record

### Option A: EOA controlled by tECDSA (current design state)
- The `bridge_canister` canister signs with tECDSA → an EOA address on EVM
- ✅ Simple to implement
- ⚠️ Hard to explain to a regulator
- ❌ If the canister can be upgraded without governance, there is unilateral control

### Option B: Gnosis Safe (signer = the canister's tECDSA address)
- The Safe is the contract that "holds" the USDC
- The only signer is the canister's tECDSA address (no humans)
- ✅ More auditable — the Safe is a well-known standard
- ✅ A regulator can see the Safe's rules on-chain on Etherscan
- ✅ Future multisig possible (add CMF as an emergency co-signer)
- ⚠️ Requires deploying a Safe on EVM + wiring

### Option C: Custom EVM Escrow Contract (immutable)
- Custom contract with hardcoded rules: "only release USDC to the user if there is a verified ckUSDC burn on ICP"
- ✅ The strongest argument: the contract is immutable, nobody can change the rules
- ✅ Zero human discretion over the funds
- ❌ More EVM contract audit work
- ❌ No flexibility for future adjustments without a redeploy

### **Recommendation: Option B (Gnosis Safe) in V1 → Option C in V2**

In V1, the Gnosis Safe is the most legally defensible architecture because:
1. It's a standard audited and recognized by international regulators
2. The rules for who can sign are transparent on-chain
3. It can be presented to CMF as "institutional multisig where GreyValley CANNOT move funds without the ICP protocol"
4. Future: add CMF or an independent trustee as a 2-of-3 co-signer → opens the door to the sandbox without losing the architecture

## 8. "Public Software" Argument — CMF Communication Guide

### The principle

CMF can ignore a technical argument but cannot ignore a communication pattern: if the platform is promoted as "a financial service that gives you a return," the regulator treats it as such even if technically it is something else. Communication framing is as important as architecture.

### What GreyValley IS (and how to say it)

> "GreyValley is an open-source interface that facilitates interaction with DeFi protocols deployed on the Internet Computer Protocol. The protocol's smart contracts are public, auditable, and operate without GreyValley's intervention once deployed. Conversion services between Chilean pesos and digital assets are provided exclusively by Koywe SpA, an entity regulated under Ley 21.521."

### PROHIBITED copy (triggers regulatory risk)

| ❌ Do NOT say | ✅ Say instead |
|-------------|------------------|
| "Deposit with GreyValley" | "Interact with the protocol using GreyValley" |
| "GreyValley gives you an X% return" | "The protocol generates yield from these sources: [...]" |
| "Your funds with GreyValley" | "Your assets in your wallet, managed on-chain" |
| "Buy/sell through GreyValley" | "Koywe (regulated third party) provides the CLP↔USDC conversion" |
| "GreyValley guarantees the value of ckUSDC" | "ckUSDC is backed 1:1 by USDC on Ethereum, verifiable via ICP/NNS" |
| "Your money is safe with us" | "On-chain assets are custodied by the ICP protocol, not by GreyValley" |

### The three pillars of the "Public Software" argument

**Pillar 1 — Open source:** GreyValley's canister code is public on GitHub. Any developer can audit it, fork the protocol, or deploy their own instance.

**Pillar 2 — No discretion:** once the governance canister is activated (§5), no human can unilaterally change the protocol's behavior with respect to user funds. The upgrade requires a community vote + 48h timelock.

**Pillar 3 — Regulated third party for fiat:** GreyValley never touches Chilean pesos. The CLP on/off-ramp is exclusive to Koywe, which operates under Ley 21.521. GreyValley is the interface; Koywe is the financial service.

## 9. Central Technical Argument: ckUSDC 1:1 via ICP/NNS — Deep Explanation

> This is the most powerful technical argument available to GreyValley before CMF. It needs to be explained well because regulators don't know ICP. This section is written to be adapted for a CMF presentation with legal counsel.

### The problem it solves

A regulator has an obvious question: *"If the user deposits tokens that represent dollars, who guarantees that value? Who holds the real dollars?"*

The traditional DeFi answer — *"the wrapped token issuer promises to maintain the reserve"* — implies trust in a company. That's exactly what a regulator treats as counterparty risk.

**GreyValley's answer is different and verifiable:** ckUSDC is neither issued nor backed by GreyValley. It is backed by ICP's **NNS** through a distributed cryptographic protocol with no human intervention from any company.

---

### 9.1 What the NNS (Network Nervous System) is

The NNS is the on-chain governance system of the Internet Computer Protocol. It is the "algorithmic government" of the ICP network — not a company, not a foundation with unilateral powers, but a rule system executed by the protocol.

**NNS structure:**

```
ICP holders → stake ICP in "neurons" (minimum 1 ICP, min. 6-month lock)
    ↓
Neurons → vote on governance proposals
    Voting weight = staked ICP × dissolve-delay multiplier
    ↓
Approved proposals → execute automatically on-chain
    (no human intervention — the protocol executes the proposal's code)
```

**Current scale:**
- ~500,000+ active neurons across multiple countries and entities
- DFINITY Foundation has a portion of the vote, but not an absolute majority — it cannot act unilaterally
- The NNS controls: ICP protocol upgrades, subnet creation, deployment and control of system canisters

**The key point:** The ckUSDC minter canister is a **system canister controlled by the NNS**. Not by DFINITY Foundation. Not by GreyValley. By an on-chain DAO with 500K+ participants. Neither GreyValley nor anyone else can modify the rules for how ckUSDC is issued or burned without NNS approval.

---

### 9.2 What a "chain-key token" is — difference from wrapped tokens

ckUSDC is not a "wrapped" token in the traditional sense. The difference is both technical and legally relevant:

| Characteristic | Traditional bridged USDC (e.g., Multichain/Synapse) | ckUSDC (ICP chain-key) |
|----------------|-----------------------------------------------------|------------------------|
| **Who custodies the USDC on Ethereum** | A company or multisig with human signers | An EVM address controlled by threshold signatures from 28+ independent ICP nodes |
| **Can a company move the USDC?** | Yes — whoever holds the keys controls it | No — requires >2/3 of the subnet's nodes to sign |
| **Reserve audit** | Attestation or audit by the issuing company | On-chain on Etherscan — verifiable by anyone in real time |
| **Counterparty risk** | Issuer bankruptcy or hack | None — the ICP protocol |
| **Who controls the mint/burn rules** | The issuing project's team | The NNS (a DAO with 500K+ neurons) |
| **Can GreyValley change this?** | N/A | **No** — GreyValley only uses ckUSDC, it neither issues nor controls it |

**For CMF:** The distinction between a "wrapped token issued by a company" and a "chain-key token issued by a decentralized protocol" is the difference between counterparty risk and protocol risk. CMF can regulate the former; the latter is analogous to how Ethereum's risk as a protocol escapes national regulation.

### 9.3 How 1:1 custody works — the technical mechanism

#### Step 1: Generating the custody Ethereum address

When the NNS approved the creation of ckUSDC (NNS Proposal-XXXXX, verifiable on-chain), it generated an **Ethereum address** using **Threshold ECDSA (tECDSA)**:

```
Threshold ECDSA — how it works:

28 nodes of ICP's "pzp6e" subnet (nodes operated by different entities in
different jurisdictions) run a distributed key generation (DKG) protocol:

→ Each node generates a "share" of the private key
→ No node knows the complete key — only its fragment
→ To sign an Ethereum tx, ≥ 19 of 28 nodes must collaborate
→ The result is a valid ECDSA signature without any node ever having had the complete key

Resulting Ethereum address: 0xA17a8883dA1abd57c690DF9Ebf58fD551d76042e
(USDC at this address = backing for ALL ckUSDC in circulation on ICP)
```

**What this implies legally:**
- DFINITY Foundation cannot move that USDC unilaterally
- GreyValley cannot move that USDC — it doesn't even have access to the system
- A hack of any company involved in ICP does not compromise the funds
- Compromising it would require compromising >1/3 of the subnet's nodes simultaneously — operated across multiple countries and cloud providers

#### Step 2: Deposit verification via HTTPS Outcalls from consensus

When a user deposits USDC at the custody address, the ckUSDC minter canister (NNS-controlled) needs to verify that deposit BEFORE minting ckUSDC. Here is the most technically important part for the CMF argument:

**How does ICP verify that the USDC arrived on Ethereum?**

```
The verification process (executed by the NNS minter canister):

1. The ckUSDC minter canister initiates an HTTPS Outcall to Ethereum
   RPC providers (Cloudflare Ethereum Gateway, Alchemy, etc.)

2. ALL NODES of the subnet (28 independent nodes) INDEPENDENTLY execute
   the same HTTP query to the Ethereum RPC:

   GET eth_getBalance(0xA17a8883..., "latest")
   or
   GET eth_getLogs(filter: {address: USDC_contract, event: Transfer, to: 0xA17a...})

3. Each node receives its response from the RPC and shares it with the group

4. The ICP runtime applies the "transform" canonicalization function:
   removing timestamps, request IDs, and any variable field from the response,
   leaving only the stable content (the USDC balance)

5. The 28 nodes compare their canonicalized responses:
   → If ≥ 19 nodes (>2/3) report the same balance: that balance is truth
   → If there's a discrepancy: the divergent node ends up in the minority, is ignored

6. Only when consensus of >2/3 of the nodes confirms the deposit,
   does the canister mint the ckUSDC to the user's principal
```

**Why this is NOT a centralized oracle:**

| Centralized oracle (Chainlink, etc.) | ICP's HTTPS Outcalls |
|--------------------------------------|-----------------------|
| A single oracle company queries Ethereum and signs the result | The subnet's 28 nodes query Ethereum in parallel and independently |
| If the oracle fails or lies → the system fails | A malicious node cannot affect the result — it needs to corrupt >1/3 of the subnet |
| There is a single point of failure | There is no single point of failure |
| The result comes signed by the oracle company | The result comes from the protocol's consensus (subnet BLS threshold signatures) |
| Requires trusting the oracle company | Requires trusting that >2/3 of the 28 nodes are not colluding |

**Argument for CMF:** The verification that the real USDC exists on Ethereum is not done by GreyValley or any company. It's done by the distributed consensus of 28 independent ICP nodes — mathematically, this is the same guarantee as the Ethereum blockchain's own consensus for its transactions.

#### Step 3: The ckUSDC mint

Once the deposit is verified by consensus, the NNS minter canister executes:

```motoko
// Code of the NNS ckUSDC minter canister (public, audited by DFINITY)
// GreyValley does not control or have the ability to modify this code

ckusdc_ledger.icrc1_mint({
  to     = { owner = user_principal };    // user who deposited USDC
  amount = deposited_usdc_in_e6s;        // 1:1 with the USDC on Ethereum (6 decimals)
  memo   = ?ethereum_tx_hash;            // on-chain proof of the deposit
})
```

The ckUSDC ledger canister (`xevnm-gaaaa-aaaar-qafnq-cai`) records the balance. This ledger is **fully public** — anyone can query:
- The total ckUSDC supply on ICP
- That this total supply matches the USDC at `0xA17a8883...` on Etherscan
- The complete history of every mint and burn

#### Step 4: Redemption (burn ckUSDC → USDC on Ethereum)

```
User → calls the ckUSDC minter canister: burn(amount, evm_destination)
    ↓
Minter canister → reduces supply in the ckUSDC ledger
    ↓
Minter canister → builds Ethereum tx: transfer amount USDC from 0xA17a... to evm_destination
    ↓
IC.sign_with_ecdsa() → the subnet's 28 nodes collaborate to generate the signature
    ↓
Signed tx → transmitted to Ethereum via HTTPS Outcall
    ↓
User receives USDC in their Ethereum wallet
```

**Invariant verifiable at all times:**
```
Total ckUSDC Supply on ICP = USDC at address 0xA17a8883... on Ethereum
```

### 11.4 Vector 1 — Founder identity and key management

**The most likely attack is not technical — it's operational:**

```
Attacker obtains the founder's private key (dfx identity)
    ↓
dfx canister --network ic install backend --mode upgrade <malicious_wasm>
    ↓
The malicious wasm has an unguarded drain(to: Principal) function
    ↓
All funds in the vault leave in a single transaction
```

**Why the code alone cannot defend against this:** ICP's security model delegates upgrade protection to the controller. If the controller is compromised, the protocol cannot distinguish the legitimate founder from the attacker.

**Operational mitigants (not in code, in behavior):**

| Measure | Status | Priority |
|--------|--------|-----------|
| Hardware wallet (Ledger) for the production dfx identity | ❌ Not confirmed | 🔴 IMMEDIATE |
| Production dfx identity ≠ development dfx identity | ❌ To verify | 🔴 IMMEDIATE |
| 2FA on all related services (GitHub, npm, CI/CD) | ❌ To verify | High |
| Governance canister as a second controller of bridge_canister | ❌ Not deployed | High |
| npm dependency audit of the build pipeline | ❌ Not done | Medium |

**The hardware wallet is the most impactful and easiest mitigant to implement.** A Ledger with the production identity means any `dfx canister install` requires physical approval on the device.

### 11.5 What's well covered — no action needed

**Reentrancy in `harvestVault`:** the design uses a running total (`total_yield - harvestedYieldPXRM`) instead of resetting a timestamp. `harvestedYieldPXRM` is written to `positions` BEFORE the `await icrc1_transfer`. A second concurrent harvest calculates yield=0 and returns immediately. This is the correct pattern for Motoko.

**Frontend tampering:** GreyValley's frontend is an ICP canister — it cannot be replaced without an upgrade signed by the controller. Plug Wallet shows the real destination Principal before every transaction, allowing the user to verify. ICP's certified-assets model guarantees the integrity of the served frontend.

**Rate limiting and spam:** `bridge/main.mo` has `RATE_LIMIT_MAX_CALLS = 20` per 60s per caller, and `processedPayments` prevents replay, including across upgrades (confirmed 2026-09-29: `var` field is stable by default in a `persistent actor`, see §11.2). `backend/main.mo` rejects anonymous callers on all shared methods.

### 11.6 Regulatory implications of the threat model

For CMF, the threat model has value in two directions:

**Positive argument:** the protocol was designed with explicit mitigants against the most common vectors (reentrancy, spam, replay). There is internal security-analysis documentation, which is a sign of operational maturity.

**Risk of arguing the opposite:** if CMF asks "how do you protect user funds?" and the honest answer is "governance has no real voting," that alone is enough exposure to trigger an operational review (the bridge's replay vector was investigated and dismissed, see §11.2). That's why implementing real governance (§11.3) remains a prerequisite before any formal contact with CMF.

## §12 SFA-Sandbox — Chile's Open Finance Infrastructure (Fintech Law 21.521)

### 12.1 What is SFA-Sandbox

**SFA-Sandbox** (`sfasandbox.cl`) is Chile's open finance testing environment, operated under **Ley 21.521 (Fintech Law)** and CMF's General Rules (Normas de Carácter General, NCG) **502** and **514**. It implements the international **FAPI 2.0** standard (Financial-grade API), the same one used in UK Open Banking and Brazil's PIX.

It is the technical equivalent of the "regulatory sandbox" that payment-service operators must pass to obtain CMF accreditation. Any company wanting to be a **PISP** (Payment Initiation Service Provider) or **AISP** (Account Information Service Provider) in Chile needs to operate against these APIs.

**Direct relevance for GreyValley:** Koywe is already accredited as a PISP under this ecosystem — meaning that when GreyValley uses Koywe for fiat on-ramp/off-ramp, GreyValley inherits FAPI 2.0 compliance *with no effort of its own*. In Phase 3, GreyValley SpA could register directly as a PISP+AISP, eliminating Koywe's commission on the fiat side.

---

### 12.2 Available APIs and relevance for GreyValley

| API | Endpoint | What it does | Relevance for GreyValley |
|-----|----------|----------|-------------------|
| **OAuth2 Consent** | `POST /api.php?action=consents` | Redirect flow to obtain user consent | Base of the flow; Koywe handles it in Phase 1 |
| **OAuth2 Token** | `POST /api.php?action=token` | Exchange code for a Bearer JWT | Needed for AISP and PISP |
| **CIBA (backchannel)** | `POST /api.php?action=ciba_auth` | Starts authentication without a redirect (push to mobile) | High relevance: no-browser flow → ideal for the GreyValley mobile app |
| **CIBA token poll** | `POST /api.php?action=ciba_token` | Polling until the user approves in their bank | Needed if GreyValley implements CIBA directly |
| **PISP — initiate payment** | `POST /api.php?action=payments_pisp` (FIX 2026-09-14: it was `action=payments`, wrong endpoint) | Debits a bank account → TEF (electronic funds transfer) to a destination account. ### 12.3 Chaos Engine

SFA-Sandbox has an activatable chaos engine that simulates real banking failure conditions:

| Chaos mode | Effect | How it affects GreyValley |
|-----------|--------|----------------------|
| **Latency +3500ms** | Every endpoint takes an extra 3.5s | The canister's HTTPS Outcall timeout must cover this |
| **HTTP 500 collapse** | Endpoints return random 500 errors | GreyValley needs exponential-backoff retry |
| **Infinite pending CIBA** | Auth never completes | Configurable user-wait timeout (e.g., 5 min) |

**Recommended use:** before connecting Koywe in staging, run the on-ramp flows against the chaos engine. If GreyValley survives chaos mode without leaving funds in an inconsistent state, the system is robust for production.

It's also useful for testing the canister's **circuit breaker**: if the bank is down per NCG 514, the canister should reject the deposit with a clear message before attempting the PISP.

---

### 12.4 ICP HTTPS Outcalls — Direct integration from the canister

**Standard architecture (with a backend server):**
```
Mobile app → Node.js Backend → SFA API → bank
```

**ICP architecture (no backend):**
```
Mobile app → ICP Canister → HTTPS Outcall → SFA API → bank
```

The canister calls `sfasandbox.cl/api.php` directly (or, in production, the real SFA API) via HTTPS Outcalls. The subnet's 28 nodes make the call independently, canonicalize the response, and ≥19/28 must agree on the result before the canister processes it.

**Implication:** there is no Node.js backend server that can be compromised, shut down, or that causes a single point of failure between the canister and the banking system. The PISP logic lives *in the canister*.

**Limitation to consider:** HTTPS Outcall responses must be deterministic across the 28 nodes. If SFA returns a different `x-fapi-interaction-id` on each request, the canister must use `transform` to strip those fields before consensus.

```motoko
// Example: transform to remove non-deterministic headers
public query func transformSFAResponse(raw : Types.TransformArgs) : async Http.HttpResponsePayload {
    {
        status = raw.response.status;
        body = raw.response.body;
        headers = []; // remove headers with unique timestamps/IDs
    }
};
```

### 12.6 Relation to §6 — CMF argument

The existence of SFA-Sandbox and Koywe's FAPI 2.0 compliance **strengthens GreyValley's regulatory argument** before CMF:

1. **We're not an opaque system:** the entire fiat flow enters/exits through regulated banking APIs (NCG 502/514), not informal channels.
2. **Koywe as a regulated buffer:** GreyValley does not need its own accreditation in Phase 1/2 because the PISP sits on Koywe's side (a CMF-regulated entity).
3. **Auditable architecture:** HTTPS Outcalls from the canister to the SFA APIs are recorded in the subnet's consensus logs — any auditor can verify what calls were made and when.
4. **Progressive compliance roadmap:** instead of "we'll break the law and ask forgiveness later," GreyValley presents a Phase 1→3 path where at every stage there is a regulated actor responsible for the fiat.

**Risk to manage:** if CMF changes NCG 502/514 or adds FAPI 2.1 requirements, GreyValley inherits that change through Koywe in Phase 1. The canister only calls Koywe's API — Koywe absorbs the regulatory changes. This is an architectural advantage, not technical debt.
